# MessMind — EDA Report (Phase 3)

> **Data:** `data/raw/messmind_training_data.csv` (1,337 rows × 20 columns, 2026-07-01 → 2026-09-28).
> **All data is SYNTHETIC** (generated by `src/generate_data.py`, seed 42). Every pattern below was
> built into the simulator; none of it is evidence about how a real mess behaves.
> Source of every number: `notebooks/01_eda.ipynb` (executed top to bottom without errors).
> Figures: `reports/figures/eda_*.png` (generated by the notebook).

## 1. Important patterns

| Pattern | Evidence (notebook section) |
|---|---|
| **Meal type** is the biggest driver of demand per dish | Breakfast mean 270, lunch 498, dinner 493 consumers per dish (§6) |
| **Dish identity** matters a lot | Rice at lunch averages 682 and Lauki Sabzi 131; spread within one dish is std ≈ 55 (§6) |
| **Recent history** is the strongest single predictor | corr(`historical_dish_demand`, target) = 0.91; "same as last 5 servings" gives MAE ≈ 57, bias ≈ 0 (§8.1) |
| **Taps are informative but are NOT consumption** | corr = 0.84; actual > taps in all 1,337 rows; actual ≈ 2.6 × taps (§7) |
| The taps-to-consumers ratio **depends on dish category** | median actual/taps: staples ≈ 2.9, desserts ≈ 1.9, non-veg mains ≈ 2.0 (§7) |
| **Calendar effects** are large (measured against each dish's own history) | holiday −19 to −28 pts, weekend −10 to −30 (strongest at breakfast), exam +7 to +14, festival dinner +18 (§8.3) |
| **Weather**: rain matters a little; heat almost not at all | rain +14 pts breakfast, +6 lunch, +2 dinner; hot days ≈ −2 pts (§8.3) |
| **No long-term trend** | mean per dish 413 (first 45 days) vs 428 (last 45 days); the small rise coincides with exams (§9) |
| Students eat **several dishes** per meal | dish servings per meal reach ~3,900 for 1,000 students (§9) |

## 3. Potentially useful features

* **Strong:** `historical_dish_demand`, `interested_taps`, `meal_type`, `dish_name` / `dish_category`.
* **Useful in combination:** `total_responses` (turns taps into a response rate), `is_weekend`, `is_holiday`,
  `is_exam_day`, `is_festival`, `rainfall`, `historical_dish_rating` (r = 0.32).
* **Candidate engineered features for Phase 4** (all computable before the meal):
  * `tap_share = interested_taps / total_responses` (raises the correlation from 0.84 to 0.89 in normalised form)
  * `response_rate = total_responses / total_students`
  * `num_dishes_in_meal` (menu size)
  * `dish_times_served_before` / `is_new_dish` flag
  * a historical taps-to-consumers ratio per dish or category, using **past rows only** (`shift(1)`)

## 4. Features requiring caution or exclusion

| Column | Decision | Reason |
|---|---|---|
| `actual_dish_consumers` | **Exclude from inputs (target)** | It is the answer the model must predict |
| `data_source` | **Exclude** | Metadata; always "synthetic" |
| `date` | **Exclude as raw input** | Used for splitting; its useful parts are already separate columns |
| `total_students` | **Exclude or keep only inside ratios** | Constant in this data |
| `previous_meal_attendance` | Caution | Weak overall (−0.09) because breakfast follows dinner; 0.10–0.24 within a meal type. The backend may not record it (contract open question 6) |
| `previous_leftover_kg` | Caution | Weak link to next demand (r ≈ 0.10–0.16). Depends on the backend recording leftovers |
| `historical_dish_rating` | Caution | Moderately useful, but its past-only construction could not be re-verified from the CSV (ratings are not stored) |
| `day_of_week` + `is_weekend` | Redundant (r = 0.79) | Harmless for tree models; keep both or pick one |
| `temperature` | Low value | Almost no effect in this data |

## 5. Leakage findings — **all checks passed**

1. **Availability:** every input column is "known before the meal" in the data dictionary; only the
   target, `data_source` and raw `date` are excluded.
2. **No post-meal inputs:** every leftover, rating or attendance column is a `previous_` or `historical_`
   value, and no input has |r| > 0.95 with the target (highest is 0.91).
3. **History is past-only:**
   * `historical_dish_demand` recomputed with a past-only formula matches **1,137 / 1,137** checkable rows,
     against **6** for a formula that wrongly includes the current row.
   * `previous_meal_attendance`: r = 0.86 with the *previous* meal's servings and −0.12 with the *current* meal's.
   * `previous_leftover_kg` (within each dish): r = −0.78 with the *previous* serving's consumers and −0.03 with the *current* one.
4. **Not verifiable from the CSV:** `historical_dish_rating`, and the first ~200 rows whose history comes
   from the 21-day warm-up. These rely on a code review of the generator (`shift(1)` before `rolling`).

## 6. Recommendations for Phase 4 (preprocessing & feature engineering)

1. **Split by date, not randomly**, and decide how to handle the exam gap. Options:
   (a) accept it and report exam-day error separately;
   (b) use a time-series cross-validation (expanding window) so later folds contain exams;
   (c) regenerate with exams spread across the period. That would change the Phase 2 data, so you decide.

   **DECISION (2026-11-13): option (a).** Keep the plain chronological 70/15/15 split. Phase 5 must
   report error on exam days separately, and state that training contained no exam days.
2. **Missing history (1 row now, many with real data):** do not drop silently. Add an `is_new_dish` flag
   and fill history from a **past-only category-level average**, or a training-set statistic.
   Compute any fill value on the **training split only**.
3. **Encode categoricals:** `meal_type` and `dish_category` (one-hot); `dish_name` (one-hot or target-free
   ordinal). Decide how to treat dishes unseen in training: fall back to `dish_category`.
4. **Drop from X:** `actual_dish_consumers` (it becomes y), `data_source`, raw `date`, constant `total_students`.
5. **Add ratio features** (`tap_share`, `response_rate`) and menu size; keep any new history features past-only.
6. **No scaling is needed for tree models**; keep a scaled pipeline only if a linear baseline is added.
7. **Do not remove outliers.** They are valid rainy days, valid leftovers and valid ratings.
8. **Baselines to beat in Phase 5:** (i) `historical_dish_demand` (≈ MAE 57 on all rows; recompute it on the test split);
   (ii) `interested_taps × historical ratio`.
9. **Fit all preprocessing on the training split only**, then apply it unchanged to validation, test and the API.

## 7. Limitations caused by synthetic data

* Every relationship (taps ratio ≈ 2.6, holiday −25%, rain +14% at breakfast, and so on) was **designed into the
  simulator**. Good model scores will show the model can recover those rules, not that it works in a real mess.
* Real data will have things the simulator lacks: changing enrolment, menu changes, missing admin entries,
  data-entry errors, app adoption that changes over time, and many more new dishes.
* 90 days and a single exam block are too few to learn rare-event effects reliably.
* `total_students` is fixed at 1000, so the model never sees how demand scales with mess size.
* Leftovers come from a fixed kitchen plan, so they don't react to taps or predictions as they would in reality.
