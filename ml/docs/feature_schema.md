# MessMind ML — Preliminary Feature Schema (v0.1, draft)

> Status: **draft** (design notes). The **exact columns of the generated dataset** are
> listed in [data_dictionary.md](data_dictionary.md), which is produced by
> `src/generate_data.py` and is the source of truth. Some ideas below (e.g. `interest_rate`,
> conversion-rate features) are planned for Phase 3 feature engineering, not yet in the CSV.

## 1. What one row represents

**One row = one dish served at one meal.**

Key: `(meal_id, dish_id)`. A Monday lunch with 6 dishes produces 6 rows.

## 2. Prediction target

| Column | Type | Description |
|---|---|---|
| `actual_consumers` | int ≥ 0 | Number of students who actually took this dish at this meal. Entered by admin **after** the meal. |

`interested_taps` (app taps) is an **input feature**, never the target.
`actual_consumers` is the **target**, never an input for the same meal.

## 3. Feature groups

### 3.1 Identifiers (used for joining / splitting, **not** fed to the model)

| Column | Type | Notes |
|---|---|---|
| `meal_id` | str | Unique per (date, meal_type). |
| `date` | date | Used for chronological splitting. |
| `dish_id` | str | Stable ID for a dish across menus. |
| `dish_name` | str | Human-readable; not a model input. |

### 3.2 Calendar / context (known before the meal)

| Column | Type | Notes |
|---|---|---|
| `meal_type` | category | `breakfast`, `lunch`, `snacks`, `dinner`. |
| `day_of_week` | int 0–6 | Derived from `date` (0 = Monday). |
| `is_weekend` | bool | Derived. |
| `is_holiday` | bool | From academic calendar. |
| `is_exam_day` | bool | From academic calendar. |
| `total_students` | int | Students registered with this mess on that date. |
| `num_dishes_in_meal` | int | Size of the menu for that meal (more choice → lower per-dish uptake). |

### 3.3 Dish attributes (known before the meal)

| Column | Type | Notes |
|---|---|---|
| `dish_category` | category | e.g. `staple_rice`, `bread`, `dal`, `main_veg`, `main_nonveg`, `side`, `dessert`, `beverage`. Lets the model generalise to new dishes. |
| `is_veg` | bool | |
| `is_special` | bool | Festival / special item. |

### 3.4 Pre-meal app signals (known before the meal)

| Column | Type | Notes |
|---|---|---|
| `interested_taps` | int ≥ 0 | Students who tapped "interested" for this dish. |
| `total_responses` | int ≥ 0 | Distinct students who tapped at least one dish for this meal. |
| `interest_rate` | float | `interested_taps / total_students`. |
| `dish_share_of_responders` | float | `interested_taps / total_responses` (0 if no responders). |

### 3.5 Historical features (**leakage-sensitive**)

Every value below must be computed **only from meals strictly before the
current meal's date/time**. In pandas: sort by time, `groupby(dish_id)`, then
`.shift(1)` **before** `.rolling()` / `.expanding()`.

| Column | Type | Notes |
|---|---|---|
| `dish_times_served_before` | int | Count of previous servings. 0 = new dish. |
| `days_since_dish_last_served` | float | NaN/large sentinel if never served. |
| `dish_hist_mean_consumers` | float | Mean `actual_consumers` over last N servings. |
| `dish_hist_conversion` | float | Mean of `actual / interested` over past servings (how reliable taps are for this dish). |
| `category_hist_conversion` | float | Same at `dish_category` + `meal_type` level — fallback for new dishes. |
| `meal_type_hist_attendance_7d` | float | Recent average attendance for this meal type (from past meals only). |

## 4. Columns that must NEVER be features

| Column | Why |
|---|---|
| `actual_consumers` (same meal) | It is the target. |
| `leftover_kg` / leftovers | Recorded after the meal. |
| `prepared_quantity` | Decided using the prediction; also post-hoc. |
| Actual total attendance for the same meal | Known only after the meal. |
| Any rolling stat that includes the current row | Leakage. |

## 5. Splitting & evaluation rules

- Split **by date**, not randomly: earliest ~70% train, next ~15% validation, last ~15% test.
- Baseline to beat: `interested_taps × historical conversion rate` (and a simple per-dish historical mean).
- Metrics: MAE, RMSE, and MAE per `dish_category` / `meal_type`.
- All results on synthetic data must be labelled **"synthetic"**.

## 6. Data provenance

| Flag | Meaning |
|---|---|
| `data_source = "synthetic"` | Generated by our simulator. Metrics do not reflect real-world accuracy. |
| `data_source = "real"` | Exported from the MessMind backend (completed meals). |

Real and synthetic rows must never be mixed silently; the column is kept on every row.
